2 · Three options at 200+ notes

hypothetical: a tag holding 438 notes, 200/page → 3 pages

Every option keeps the existing notes-head label reporting the honest total (“438 notes”) — that sentence never changes. Each option adds its own, differently-placed way of saying you are looking at one page of that total, which is the exact thing §5.5 says must never be missing.

Option A — Numbered pages, footer-anchored

footer band · numbered buttons

A dedicated footer strip appears under the note list, only at 200+, with page-number buttons (current page filled with the accent) plus prev/next chevrons. Closest in kind to a traditional results pager.

Cost

The range text itself carries the total — there is no separate label to keep in sync with it, and no way to misread it as a subset with no escape hatch.

Honesty rule kept most directly: one string, “Showing 1–200 of 438”, states the subset AND the total together — the single clearest reading of §5.5's rule of anything on this board.

Cost

New footer band like A, but the widget itself is simpler than A's — no page-number list, so it needs no ellipsis/truncation logic no matter how large the vault grows. Scales to any total for free.

Risk

3 · Also considered

Option D — don't build a pager visual yet

Listed for completeness, per the standing invitation to name this if it's the honest answer. It is not recommended here: the user's 2026-08-02 call (“if more than 200 notes, add page system”) already closed the should we build it question. What was still open was only what it looks like, and §5.5.1 explicitly asks for this exact mock before the feature can ship. Deferring the visual again would relitigate a decision that is already settled, not answer the one still open.

4 · Recommendation

Option C — range readout + steppers, footer-anchored.

It states the §5.5 honesty rule in the single most literal form available (total and subset in one sentence), it never touches the notes-head row that has a proven overflow failure at 480px, and unlike numbered pages it needs no additional truncation logic no matter how large a future vault's page count grows — the same simple widget serves 3 pages or 300.

§7 floors checked against every option above

  • Every pager control is a real <button>, never a styled <div>.
  • Icon-only prev/next controls carry an aria-label that restates the current position after every click, the same rule §4.5/§7 already applies to the sort button.
  • Disabled prev/next (first/last page) uses the real disabled attribute, not a visual-only fade.
  • The current page (Option A) is never colour-only — it also carries the visible number and aria-current="true".
  • No new easing curve or duration: hover uses the existing .btn-hover recipe only, exactly as §8 of the parent spec requires.
