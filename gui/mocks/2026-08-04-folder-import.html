Importing a folder-organised vault — FR-23 Option C

the one thing that writes into note bodies 2026-08-04 · s140

You pre-approved this and confirmed it again this session. Four choices are left, and each one changes what a stranger's vault looks like after they say yes. Everything below is drawn from the real surfaces, not described.

Settled before you choose — verified at source, not assumed:
  • The import writes two things per folder: the body tag #project@<folder> and a .projects.toml entry. resolve_project (project_registry.py:183) resolves a tag only if the registry also holds the name — tag alone leaves the note reading loose, and the tidy pass would move it anyway. That is exactly the failure the Daily probe hit.
  • Bodies are touched only on an explicit yes, with the change shown first. Nothing here runs automatically, ever.
  • Files do not move. The import makes the folders legitimate; it never re-paths a note.
  • _scratchpad, _trash, _attachments, _mobile_inbox and _loose are never candidates.
  • A note that already carries a #project@ tag is skipped, not re-tagged.

The combination I would ship: A1 + P1 + G1 + N1. The offer meets the user at the moment their tree is about to flatten, the tag lands exactly where #daily already lands, the folder is the unit of consent, and the product never renames anything the user named. It is also the smallest build: one button on a strip that already exists, one placement rule the code already has, one list, and a skip. N3 is the one worth adding later if real vaults turn out to be full of spaced folder names — it is additive to N1, not a different design.
