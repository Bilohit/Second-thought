Two characters the desktop cannot draw, and what to use instead

Every option below is rendered in the exact 229-glyph subset the desktop ships, in the real activity rows, toasts and prompts that carry them. If an option looks right here, it looks right in the app. Pick one per group; each lands in DECISIONS.md §5 before Phase 3 touches a string.

What the subset actually holds — read from the shipping woff2 this session

Above U+2000 the desktop's IBM Plex Mono carries exactly 21 glyphs. The Arrows block contributes two: ↑ and ↓. Horizontal arrows are not in it, so → is the only arrow the mock uses that breaks — "saved … full window NOTES ↑" already renders correctly today.

One cost that applies only to option 2

Activity rows are built today as strings with light markup — activityAdd("s", "synced <b>3 notes</b> → drive"). An inline SVG means those rows become JSX fragments rather than strings, so the row builder and its tests change shape. Options 3–5 are a find-and-replace inside the existing strings. That is the whole trade: option 2 is the most on-identity and the only one that also costs structure.

What this decides, and what it does not

Choosing from these two groups closes the glyph debt without touching the font — @fontsource's latin subset stays, main.tsx and typeface.test.ts are untouched, and nothing new is bundled.

★ needs no decision: no face has it and the mock never uses it. LIST/STARS is a word plus an inline SVG.

The phone is unaffected either way — its 930-glyph face draws all three today — but it takes the same replacements, because the two apps must not disagree about what an activity row says.
