Calendar for reminders — s147 decision board

Reminders already work on both platforms and already cross devices: the truth is the note's remind_at frontmatter key, LWW-merged by the ordinary Drive sync. Nothing here proposes a new store. What is missing is a place to see them all, and a way to write a note that fires on a chosen day. Pick one option per section.

Everything below renders in the shipping face (IBM Plex Mono +0.01em) at the shipping scale (9/10/11/12/13/16/20/22), on 0-radius bordered surfaces. Colour is semantic only: red = overdue, grey = fired, plain = upcoming.

0What exists today — verified at source, not carried

This is the ground the calendar stands on. Both halves are real and firing; neither is a stub.

PHONE — WORKS

Set, scheduled, delivered

ReminderSheet.tsx writes remind_at · notifications.ts:56 schedules · Android exact-alarm path survives Doze · listed at Settings › Data › Reminders.

The Today tab's deletion took only a duplicate agenda row and a due-count gauge. The feature itself never lived there.

DESKTOP — WORKS

SQLite schedule + real OS task

reminders.py holds a scheduling table; sync_reminders_from_notes:204 reconciles it from each note's remind_at on every sync pass — files stay the truth. Windows Task Scheduler fires even with the app closed.

Rendered today as a flat list on the old Dashboard only.

THE GAP

No calendar anywhere

No month grid, no date picker, no agenda, on either platform. No date library is installed on either side — and none needs to be.

And no desktop path writes remind_at into a note. POST /reminders writes the SQLite row only. Phone has setRemindAt; desktop has nothing equivalent. That is the one genuinely new capability below.

5Time — you ruled it optional, so the question moves

Your call: "time is not required. Start of the day is the default state. The user can then choose to add the time." That settles the interaction. It opens a different question the interaction cannot answer: a notification has to fire at some instant, and remind_at is a single ISO timestamp with no all-day flag. Pick what "start of day" means when the alarm goes off.

FIRING — OPTION 1Literally 00:00
remind_at: 2026-08-09T00:00

Simplest possible reading. No new field, no new concept, no config.

It buzzes you at midnight, and on the phone that is a real alarm through the exact-alarm path that deliberately survives Doze. Almost never what anyone wanted.

FIRING — OPTION 2, RECOMMENDEDA configured day-start hour
remind_at: 2026-08-09T08:00

Settings › day starts at 08:00 — one value, both apps, shown as ALL DAY wherever the reminder is displayed.

"Start of day" becomes your start of day, not the clock's. The stored value stays a plain timestamp, so nothing about the contract, the sync or the schedulers changes.

Cost: one settings row per app, and the two must agree or the same note reads as a different hour on each device. Honest limit: a note created on the phone at 08:00-start and read on a desktop set to 09:00 still shows ALL DAY, but its stored instant is 08:00.

FIRING — OPTION 3Date-only is silent
remind_at: 2026-08-09T00:00

Shows in the calendar and the day list. No notification until you add a time.

Never buzzes at an hour you did not pick. The calendar becomes a planner, and the notification is an opt-in on top of it.

Two classes of reminder that look identical but behave differently. A reminder that does not remind you is the kind of thing you discover the day after it mattered.

★★ FOUND WHILE VERIFYING THIS SESSION'S BUILD — A DESKTOP REMINDER NEVER REACHES THE PHONE

The desktop editor's Reminder row calls createReminder(note.path, label, when) (NoteEditor.tsx:1153), which is POST /reminders — a SQLite row only. Nothing writes remind_at into the note. And sync_reminders_from_notes runs one way: notes → table, never table → notes.

So today: a reminder set on the phone fires on both devices. A reminder set on the desktop fires on the desktop and the phone never learns about it — and it is invisible to the desktop's own calendar, since the calendar reads the same notes the sync does. This is pre-existing, not caused by the port, but the calendar cannot be built on top of it without deciding: the composer writes remind_at to the note, and the editor's Reminder row should move to that same path so both devices agree.

★ ONE ASYMMETRY WORTH DECIDING NOW

Desktop's DELETE /reminders/{id} removes the SQLite row only. The note still carries remind_at, so the next sync pass's sync_reminders_from_notes recreates the row — a dismissed reminder comes back. That is pre-existing, not introduced here, but a calendar makes it visible.

The fix that fits the locks: the calendar's "done" clears the note's remind_at — files stay the truth and the DB follows, which is the direction every other cache in this product runs. Confirm you want that, since it edits the note's frontmatter (never its body).

Deliberately NOT in scope

  • No calendar-events import. expo-calendar stays dropped; this reads your notes, not your phone's calendar. Say so if you want the opposite.
  • No recurring reminders. remind_at is a single timestamp; repeats need a contract change and a whole rules UI.
  • No new tab, no new store, no new dependency on either platform.
  • No month view in the pill. The pill is Phase 5 and motion-frozen; a calendar panel there is a later, separate call.

Open sub-questions, answered by picking above

  • Which days can you create on? Assumption: any day, including the past — a past date creates a note whose reminder is already overdue, shown red. Cheaper than blocking it.
  • Timezone. remind_at is stored as written; a reminder set on the phone in one zone fires at that clock time on desktop. Matches today's behaviour — not changed here.
  • How far the calendar scrolls. Assumption: month at a time, arrows both ways, "today" always one gesture away.
