Flow review decisions — the Projects screen

Three holes the 2026-08-02 live pass found in the full-window Projects screen, each one a design decision, not a bug fix. Board of options for each, side by side, so you can point and say “B”. Visual language is matched 1:1 to gui/mocks/2026-08-01-projects-fullwindow-v3.html, the screen’s own source of truth — same tokens, same weights, same rhythm. Nothing here writes to a note body; nothing here is emoji.

Where reading the real source corrected this brief: the brief names the --ctl-face / --surface-2 collision a light-theme ceiling. Reading gui/src/index.css’s two theme blocks directly, the two tokens are identical in both themes — dark: #404040 / #404040; light: #cccccc / #cccccc. So every option below keeps raised controls off --surface-2 in dark mode too, not only light. Demonstrated once, in both themes, right below — not re-proven per option.
Everything else in the brief — the single caller of createProject/moveToTrash (VaultManager.tsx:899/845), the stats → library alias (App.tsx:242), the missing setProject/moveToProject/assignProject, the exact live copy strings — checked out verbatim against the current code.

A · modal

Easiest to validate name + description together, but is a whole new overlay surface: focus trap, escape key, backdrop click, all to build and test.

B · inline

Zero new surfaces, and works at zero projects for free. But a mid-grid input needs its own Enter/Escape/blur-cancel handling, and a long name in a narrow tile needs its own truncation rule.

C · promoted box

Reuses 100% of existing CSS, cheapest to ship. But it overloads one box with two jobs — machine-proposed and user-typed — so “Inbox suggests” must become conditional copy or it lies half the time.

Recommendation

B, inline. The screen already separates “name the project” (this step) from “describe the project” (the existing autosaving desc-area in the pane) — a two-field modal would duplicate work the pane already does one keystroke later. Delete-note: the hover-icon pattern, because it matches the danger-icon language the pane head already teaches for deleting a project, rather than adding a second one.

Fork 3

“Assign this note to a project” does not exist — and the copy blames the phone

Grepping the GUI for setProject / moveToProject / assignProject returns zero hits, and a note row’s only interaction is opening the note. This is likely correct by architecture, not omission: a note’s project is the body tag #project@<name>, and a note’s body is sacred — only the user’s editor may write it. “Assigning” genuinely means editing the body, which no panel here is allowed to do on the user’s behalf. The problem is the screen never says so — its copy tells a desktop-only user that a different device does the filing.
