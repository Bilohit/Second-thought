Projects, full window: three ways to weight description against notes

A3 is settled and is not on the table here. The parent spec §6 item 1 already closed the layout strategy for this surface: a split panel, project list on the left, that project's description editor and notes on the right, no drill-in, and the left rail carries the tile/list toggle. All three options below are A3. They differ only in how much of the right pane the description editor is allowed to take from the notes list, and how loud the rail is.

The real trade-off you are picking: A favours density (most information per pixel, closest to today), B favours reading notes (the notes list dominates, description is one click away), C favours description quality — which is the one that makes phone auto-assignment work, because the phone matches a new note semantically against the description text you wrote.

A note's project comes from a body tag like #project@research; exactly one project per note; a note with no tag is loose, which is normal, permanent and never nagged at. Both apps group by the tag, never by a path, and no surface presents a path as the source of truth. Tile mode shows project groupings; list mode shows individual non-action tags only (sys/* and #project@ are filtered out). Deleting a project removes the registry entry and nothing else — its notes go loose, no note is ever destroyed by a project operation (§5). The engine may propose a new project from an Inbox item but may never create one: approval is always yours.
Two findings from the live smoke run against your actual vault, recorded here so you see them next to the design.
The index's project column is a stale derived cache. Task 11 renamed category to project without re-deriving the values, so /stats and /search?project= currently report personal, work and recipes as projects that do not exist in any registry. Every count those routes return today is describing the deleted taxonomy, not the new one.
project_registry.rebuild_from_vault has zero non-test callers. It was built and never wired to anything. Whichever option wins, the "rebuild from the tags in my vault" recovery path this page will want does not currently exist as a reachable action.

Option A — "Ledger": density

most information per pixel, closest to today

A dense single-column rail: name left, note count right-aligned, nothing else. The right pane splits horizontally — a compact always-editable description strip on top (no modal, no expand step, you just type in it) and the notes list filling everything below. Because A is the density option, its rail control is three positions rather than two: tiles (a 2-column project grid), rows (the dense single column), and tags (list mode — individual non-action tags only). Suggestions live as a quiet strip pinned to the bottom of the rail, so they never displace notes.

1100 x 680 — populated. Click a rail row to select it; the rail control is live.

Populated. The description strip is 3 lines and always live — edits commit on blur, there is no Save button to hunt for. The cost of that compactness is that a long description scrolls inside a 3-line box, which is exactly the thing risk 4 in §11 warns about: the field the phone depends on is the smallest thing on the page.

1100 x 680 — first open, and this is your vault as it actually is today

First open. Zero registered projects, 17 loose notes, and no error anywhere. The rail holds exactly one entry — loose — and the pane shows those notes as an ordinary, readable list. The invitation to make a project is one calm button; nothing counts down, nothing is red, nothing calls this state incomplete.

Option B — "Workbench": reading

the notes list is the page

The narrowest rail of the three: names only, count as a quiet right-aligned numeral, no descriptions, no snippets. The right pane is given almost entirely to notes, at a larger row height that is comfortable to read down. The description collapses to a single-line header strip showing its first words; clicking it expands a full editor in place (live — try it), and it collapses again on save. Deliberately secondary, always exactly one click away.

1100 x 680 — populated. The description strip expands and collapses; the rail control is live.

Populated. Best option for the day-to-day act of "open a project, scan what's in it". The risk it accepts: a description you never expand is a description you never write, and an empty description is what degrades phone matching. B answers that with the collapsed strip's own copy — when the text is missing, the strip says so in the same place the text would be.

1100 x 680 — first open

First open. Same calm framing, but B's larger note rows mean the 17 loose notes read as a proper reading list rather than a backlog. The suggestion strip sits above them where a banner would go, and can be dismissed without touching anything else.

Option C — "Card": descriptions are load-bearing

optimises the field the phone actually reads

The right pane leads with the project itself: the name as a large heading, and underneath it a genuine multi-line editor, roomy enough that writing three sentences feels natural rather than grudging. Under the editor is a live quality hint that explains, in one line, why the text matters: the phone embeds this description and matches new captures against it, so a blank one means the matcher has nothing and correctly gives up rather than guessing (§11 risk 4). The rail carries a one-line description snippet per project, so a blank one is visible from across the page. Notes sit below as a compact table.

1100 x 680 — populated. Type in the description to watch the quality hint move; the rail control is live.

Populated. Select trip-japan in the rail to see the blank-description state: the editor is empty, the hint reads weak in yellow, and the rail row shows "no description" where the others show their first words. The cost is the obvious one — the notes table gets the smallest share of the three, roughly half of B's.

1100 x 680 — first open

First open. C's empty state is the one that teaches: because the card is the page, the first project you create lands you straight in a description editor with the quality hint already showing, which is the moment that decides whether phone auto-assignment ever works for you.

What you are actually choosing

A — Ledger

Pick this if you want to see everything at once and treat the description as a small field you occasionally fix. Least change from today. Highest risk of leaving descriptions thin.

B — Workbench

Pick this if the thing you do most is read a project's notes. Descriptions stay reachable but never take space from the list. Middle ground on the phone-accuracy risk.

C — Card

Pick this if you want phone auto-assignment to work well. It spends real screen area on the one field that drives it, and makes a blank description visible rather than silent.

All three are A3, all three carry the tile/list toggle on the rail, all three show loose as a first-class rail entry, and all three keep project creation strictly user-approved. Nothing below the neck differs; the choice is purely about where the pixels go.
