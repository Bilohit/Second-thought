FR-34 — how much of it is worth doing?

The original question was “what should the import offer for nested folders?”. That question turned out to rest on a persona the product cannot currently produce. This board carries the corrected premise and four scope options.

Every claim below was read at source today. The ledger’s FR-34 entry overstates itself in three places, noted inline.

1Where nesting can actually come from

The app never creates a nested project folder. note_dir_for returns a single name, every tidy destination is depth 1, and test_project_tidy.py:45-51 pins that invariant — it is what keeps a note’s ../_attachments/<id>/<file> references resolving. The only nesting the product itself produces is _attachments/<id>/<file>, which sits on _EXEMPT (folder_import.py:24) and can never be an import candidate.

And the import’s own docstring (folder_import.py:3-6) says what it was built for: “A vault that predates the s127 tag model organises notes in folders and carries no #project@ tags at all.” A pre-s127 Second Thought vault was also depth 1 — the app created those folders too.

SOURCE 1 — AVAILABLE TODAY

The user makes a subfolder by hand

In Explorer, or in Obsidian. Nothing forbids it — files are the source of truth. This is the only way nesting can appear in a shipped install right now.

SOURCE 2 — PARKED, NOT BUILT

vault.root pointed at a foreign tree

config.toml allows an absolute-path override, so it is technically reachable. But the first-run VaultSetup surface that would make this a real user flow is parked and unbuilt (CURRENT.md §4.1).

Consequence: the ledger’s “a user with years of nested folders … a bigger betrayal than FR-33” describes someone the product has no supported path to create. The defect is real; the persona is not.

2What actually breaks, and only then

For a hand-made subfolder, _maybe_refile_local (mobile_sync_agent.py:731) computes p.parent.parent / dest_folder / p.name. At depth ≥ 2 that grandparent is not the vault root, so it fabricates a folder one level short — and the error compounds by one level per extra depth.

It fires only on a pull or a 3-way merge (:983 and :1044) — never on the initial local→hub push. A nested note the other device never touches stays exactly where the user put it, indefinitely. Second ledger overstatement: §4.2f implies it happens as a matter of course.

Third ledger overstatement: §4.2f names one location. The identical depth-1 walk is duplicated in vault_admin._filed_notes:427-435, which is what feeds tidy — so nested notes are invisible to tidy as well as to import.

5The original offer question — now moot, kept for context

“Should the import offer Work, Acme, or every level?”

This was the first board’s A/B/C/D. It is superseded because no supported flow produces the nested vault it assumed — but two of its findings survive and constrain any future answer, so they are recorded here rather than lost:

  • A project name can never hold a path separator. ^[A-Za-z0-9][A-Za-z0-9_-]*$ excludes /, and is_valid_project_dir requires safe_name(dir) == dir where safe_name rewrites / to _. Work/Clients is refused as both a name and a dir. Nesting has no representation in the registry.
  • Tagging a nested note necessarily flattens it. Tidy destinations are contractually depth 1, so every option that tags nested notes ends with Clients/ and Acme/ rmdir’d — which would falsify the panel’s own s141 promise, “Your folders keep their names, and nothing moves.”

Considered and not offered: relax the grammar so dir can hold Work/Clients. It would preserve nesting exactly — and it is the change I would argue hardest against. safe_name’s round-trip equality is what stops scratchpad.approve_scratchpad_item (which joins through safe_subdir, and neutralises rather than refuses) from filing a note into a different directory than tidy and sync compute. Allowing a separator reintroduces the exact silent-relocation class the dir key was created to kill in FR-33, and breaks ../_attachments/ reference depth on top. It is a data-model-and-contracts.md §13.1 change with a blast radius well beyond this ticket.
